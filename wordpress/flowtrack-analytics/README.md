# FlowTrack Analytics

Install this directory as a WordPress plugin on **ikomeflow.com**. Activate it and open **FlowTrack Analytics** in the admin menu. Only users with `manage_options` can read the dashboard. Its refresh endpoint requires both that permission and a WordPress nonce. The frontend is the existing static FlowTrack app, with no subscriptions or registration added.

## Collection

`POST https://ikomeflow.com/wp-json/flowtrack-analytics/v1/collect` accepts only the exact origin `https://flowtrack.ikomeflow.com` and a body of at most 1 KiB. Legacy version 1 accepts its original six fields and event names. Version 2 accepts exactly ten fields: version, event ID, random visitor ID, random session ID, fixed event and screen names, a broad device category, browser/installed mode, a numeric app version and a safe error code (`none` for non-error events). Unknown fields, arbitrary strings and invalid IDs are rejected. Browser requests omit cookies, credentials and referrers. No secret belongs in the browser. Collection is public and cannot cryptographically prove an event is human; Origin is browser protection, not authentication. Statistics are estimates.

The app defaults to off. Equal-weight Allow and No thanks controls explain sharing with Futura Group. Existing version 1 acceptance does not authorize version 2: the expanded notice must be accepted again; earlier declines stay declined. Settings → Privacy & backups contains the toggle. Do Not Track and Global Privacy Control override consent. Revoking consent removes browser/session identifiers across tabs. Analytics receive no ledger objects, exceptions or form text. The app emits only fixed step names after successful actions. Browser identifiers rotate after 30 days; sessions are shared across tabs and renew after 30 minutes without a sent event. Heartbeats run approximately once a minute only on visible online pages with interaction in the last five minutes. No offline queue or retry/backfill exists. The independent analytics module can fail to load without preventing the main app from opening.

## Definitions and retention

- Daily active users: distinct participating anonymous browsers with an event today, in the configured WordPress timezone. This is not an account/person total.
- Live active users: distinct browsers whose latest received event is within five minutes. Closing the app can take five minutes to disappear; timers/ad blockers reduce accuracy.
- Sessions today: distinct session IDs seen today. A session spanning midnight appears on both days.
- App activity: successful transaction create/update/delete, backup download/restore, PDF export, app opens and fixed screen views. Demo ledger actions are excluded from financial feature events. No amounts, descriptions, tags, transaction IDs, dates, PINs, keys, emails, URLs, referrers or user agents are accepted.
- New/returning today: first observed in the retained 30-day history today versus seen on an earlier day. These are browser observations, not first-ever users. Identifier rotation, consent renewal, cleared storage and different devices affect counts.
- Seven-day return rate: browsers first observed 8–14 local calendar days ago, with a return on another day within seven days. Only completed follow-up windows enter the denominator. An empty cohort shows Collecting data, not zero percent.
- First-use progress: observed empty-ledger setup, successful initial PIN creation and the first successful transaction save, in that order, within the selected trend period. Existing ledgers, demo actions and steps before consent are excluded. Only step names leave the app; PINs and financial contents never do.
- Safe errors: save, PDF export, restore, startup and offline-download failures. No raw exception, stack trace, file name or user text is transmitted. Repeated identical codes are limited to once per ten minutes per page. Reports cover only observed, consenting online browsers and cannot detect every failure, especially if analytics itself is blocked.
- Device/app summaries: mobile/tablet/desktop/unknown, browser/installed mode and app version. Full user agents are interpreted locally and never sent. Legacy copies appear as unknown/legacy. A browser can appear in multiple categories during the selected period.
- Screen popularity: fixed workspace screen views and distinct participating browsers. Activity counts also show distinct browsers for feature adoption.

WordPress stores only salted hashes of random identifiers, fixed event/screen/step names, device/access categories, app versions, safe error codes, reception timestamps and local calendar days. Data older than 30 days is excluded from every query and removed by an hourly WP-Cron hook. Rate limiting stores minute-specific salted IP buckets (no raw IPs): 120 requests/minute/source address and 100,000/day globally; buckets are cleaned hourly. Hosts may keep normal access logs. Public endpoints are susceptible to fabricated traffic, and shared networks may be throttled. Plugin 1.1.0 adds four bounded columns and an index using dbDelta on upgrade; existing analytics records are preserved with unknown/legacy defaults.

## Deployment and rollback

Deploy the WordPress plugin first on Hostinger and verify migration/report access before publishing the new client. FlowTrack's static frontend is served by GitHub Pages from `ikomeflow/flowtrack`; commit the tested frontend and source to its existing main branch to trigger the existing test-and-deploy workflow. Keep older app assets so installed/offline copies continue working. The service worker downloads a complete cache under `v26-20261030-insights`, including `app-v18.mjs`, `analytics-v2.mjs` and `styles-v15.css`; existing clients can use the app's Update button. No financial records, database account tables, signing keys, SMTP setup or paused subscriptions need changing.

Rollback by reverting the frontend release commit through the existing deployment workflow and restoring the previous plugin files, or deactivating the plugin. Leave the additive analytics columns in place; do not clear visitor site data or replace the database. Deactivation stops collection/dashboard routes and unschedules cleanup; existing analytics remain in the WordPress database. If you keep the plugin deactivated, retention cleanup also stops. Do not leave retained analytics indefinitely after uninstalling.

## Validation

Run `npm run build`, `npm run check`, `npm test`, `php tests/analytics-collector.php` and `php tests/analytics-insights.php` (PDO SQLite required for controlled-history SQL tests). Browser QA should confirm both consent choices, consent renewal, the settings toggle, successful setup events, admin report changes, no analytics requests while declined, offline continuity and normal app operation when the analytics module is unavailable. Verify unauthorized report access, foreign origins, arbitrary context/private fields and unsafe errors are rejected, and duplicate events are ignored. Use a disposable browser ledger for write/export tests; never alter an existing user's ledger for QA.
